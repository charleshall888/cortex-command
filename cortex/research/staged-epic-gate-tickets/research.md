# Research: staged-epic-gate-tickets

Topic reframed during research. Entered as "adopt `/wayfinder`'s staged decomposition"; the evidence redirected most of it to an unenforced ticket vocabulary and a set of epic-closure defects. Staged emission itself was deferred, then partially revived at the Research→Decompose gate on an argument the fan-out never tested — see DR-3 and the fifth piece.

## Research Questions

1. **What is the single source of truth for `type`/`status`, and where does validation belong?** → **There is none, and there is no validation anywhere.** `type` is declared only in prose (`skills/backlog/references/schema.md:10`, `docs/backlog.md:23`). Status has five competing definitions: `common.py:181` `TERMINAL_STATUSES` (8), `common.py:1234` `_STATUS_MAP` (9 aliases), `overnight/backlog.py:38` `STATUSES` (14), `:42` `ELIGIBLE_STATUSES` (5), and `overnight/map_results.py:_TERMINAL_STATUSES` (`{merged, failed, deferred}` — different domain, colliding name). `create_item.py:210-212` and `update_item.py:506-520` are free text with no `choices=`. `overnight/backlog.py:38-44` sits under a comment reading `# Valid enum values for validation` and is referenced nowhere — the thing that looks like the enforcement point is decorative.

2. **Do `done`→`complete` and `wont-do`→`wontfix` need migration or aliasing?** → **Aliasing, already deployed.** 36 of the 38 off-vocabulary items collapse at read time through `_STATUS_MAP`. Only `deferred` is a real migration. `wont-do` is in `TERMINAL_STATUSES` but absent from `_STATUS_MAP` — terminal yet never normalized, which splits it into its own bucket in the dashboard histogram (`dashboard/data.py:1110`).

3. **Is `type` the right carrier for resolution mode?** → **No.** `backlog.md:102` routes from readiness, never type, with `idea` excepted as "a readiness statement rather than a problem-kind label" (#425). Four independent systems converged on the same axis: BPMN models assignability as semantics layered on a task, Temporal uses an `AWAITING_APPROVAL` status plus a wait-condition, Airflow an `awaiting_input` state, Camunda a per-activity property. **No new type values are warranted.**

4. **What distinguishes a decision ticket from `spike`?** → **Nothing that survives inspection.** `spike` is a genuine problem kind: 11 of 16 carry a `spec:`, the same refine-through rate as `feature` (113/164). Its only differential treatment is a scheduling weight (`_TYPE_SCORES["spike"] = 0.3`). And the learning-DoD terminal already exists — `cortex-lifecycle-wontfix` (`pyproject.toml:101`), whose `feature_wontfix` event maps to state `complete` (`common.py:469-471`). It is mislabeled, not missing: its doc reads "premise rejected," so nobody reaches for it on an investigation that succeeded.

5. **What would emitting less than a full lifecycle set cost — discovery emitting a partial piece set plus a gate, or work taking a non-lifecycle fast path — and is either warranted?** → **The fast path is not warranted (DR-2). Partial emission is unresolved and now carries a live argument for it (DR-3).** *Partial emission* runs against `decompose.md:9`, which makes a missing piece a research defect, and `decompose.md:7`, whose two-subsection input contract renders uncertainty invisible; ADR-0007 (accepted) governs the piece→ticket mapping and would need a successor. *The fast path* failed all three of its tests — see DR-2.

6. **What are correct closure semantics for an epic that gains children over time?** → **Three defects, one live.** `update_item.py:337` hardcodes `status: "complete"` on the parent regardless of the last child's terminal value (#113 reads *complete* with a `wontfix` child #124; commit `4574a216` wrote "The distribution story is now complete" into history). `:299-301` bails on an already-closed parent, so epic #9 silently absorbed child #207 **39 days after closing**. `generate_index.py:157` drops terminal items from `index.json`, so `build_epic_map` currently sees **1 of 34 epics**. A corpus scan found **0** closed-parent/open-child mismatches — so #113 is a truthfulness defect, not an invariant violation.

7. **How is a requirements-touching ticket kept from resolving as an agent file-edit?** → **It isn't, and that is by design.** `skills/build/references/review.md` §2 has the reviewer emit `## Suggested Requirements Update`; §3a auto-applies it; the instruction is explicit — *"When uncertain about drift, log `detected` — a false positive auto-applies a small update, a false negative silently hides drift."* `stage_artifacts.py:340` stages that exact path, deliberately avoiding a directory-scoped add. Reversing this retunes a tested, intentionally false-positive-biased mechanism and needs its own evidence bar.

## Codebase Analysis

**Corpus (425 items).** Types: `feature` 164, `chore` 121, `bug` 78, `epic` 34, `spike` 16, `task` 8, plus `needs-discovery`/`fix`/`enhancement`/`discovery` ×1. `idea` — declared and routing-significant — has **zero** instances. Statuses: `complete` 373, `wontfix` 25, `abandoned` 8, `superseded` 7, `backlog` 6, `done` 3, `deferred` 2, `wont-do` 1. One item carries the literal unfilled template string as its status.

**The two-axis problem.** `type` carries three jobs: problem kind (`feature`/`bug`/`chore`/`spike` — legitimate), structural role (`epic` — 0 of 34 have a `spec:`, 0 have a `parent`, and every code branch on it is structural: `build_epic_map.py:140,151`, `load_parent_epic.py:425-426`, `overnight/backlog.py:514,587`), and readiness (`idea`, `needs-discovery`, `discovery`). The one-offs sort cleanly: `task`/`fix`/`enhancement` are spelling drift; `needs-discovery`/`discovery` repeat the readiness-in-the-type-field mistake.

**`deferred` is a documented tag leaked into the status field.** `schema.md:11` defines it as a tag and directs authors to "park via a non-eligible `status` instead." `_is_deferred` (`generate_index.py:74-76`) matches **tags only**, so `status: deferred` is invisible to the feature built for parked work. And because `deferred` is in neither `TERMINAL_STATUSES` nor `_STATUS_MAP`, one deferred sibling silently prevents its parent epic from ever closing (`update_item.py:333`). Observed in wild-light: epics 236, 284, 263 all stuck at `status: backlog` with complete-plus-deferred children.

**Ticket bodies are editable, and re-authoring is in active use.** `update_item.py` writes frontmatter only — its sole writer is `_set_frontmatter_value` — but that is a verb boundary, not a capability limit: agents edit `cortex/backlog/NNN-*.md` directly with ordinary file edits. Nothing gates that write. `cortex/backlog/` is absent from CLAUDE.md's lifecycle-gated path list, the only path-inspecting PostToolUse hook returns early unless the basename is exactly `SKILL.md` (`claude/hooks/cortex-skill-edit-advisor.sh:27-29`), and `cortex/` is registered in sandbox `allowWrite`. Body rewrites happen routinely and are committed as such: `9af200e8` *"Rewrite ticket #415 body to match single-pass scope"* (+8/−4), `465c5acd` *"Reconcile ticket #412 record with appended update section"* (+46/−2), `70ffcb69` *"Rewrite #230 procedure with paired dispatch events"* (+83/−18), `f26c1392` *"Annotate #230 body: parent #228 cancelled via #246"* (+6/−0); **232 of 425** tickets carry 2+ commits. Re-authoring is therefore possible and practiced, and the decay the user reported is **not a capability gap**. Nor is it usefully treated as a reminder gap: a prompt to reconcile downstream tickets is prose-only enforcement of a sequential gate, which `CLAUDE.md:29` and `docs/policies.md:11` admit only where occasional deviation is cheap — and here the deviation *is* the reported failure (ticket 9 worked against an epic that changed at ticket 4). The unresolved question is therefore what **structural** mechanism prevents it; both candidates are evaluated under `## Architecture`.

**Migration hazards.** `update_item.py:469-477` fires on any terminal status and does two things — `_remove_uuid_from_blocked_by` (rewrites **other items'** `blocked-by` arrays) and `_check_and_close_parent`. A bulk migration through the write verb would mutate unrelated files. Precedent for a direct rewrite exists at `init/_relocation_migration.py:45`. Ordering hazard: `_check_and_close_parent` reads **raw, unnormalized** status (`:299`, `:333`) while every other reader normalizes — narrow `TERMINAL_STATUSES` before migrating and 3 `done` + 1 `wont-do` items instantly read as active. **Migrate first, narrow second.**

**Consumer-repo damage.** `pixel-art-generator` carries 33 `complete` + **6 `completed`** — in neither `TERMINAL_STATUSES` nor `_STATUS_MAP` — so six finished items sit permanently in its active index. Those tickets carry machine-written `uuid`, `schema_version`, and `lifecycle_phase: complete`; only `status` diverges, which rules out the CLI as the writer. **A write-time `choices=` in this repo would not have prevented it.** `wild-light` carries `deferred`×8, `done`×4, `open`×2.

**Routing.** After #425, `_recommendation()` (`triage.py:78-87`) is the single shared function called by both the flat Ready loop (`:176`) and `_render_epic_block` (`:103`) — `idea` → discovery, else `build` if `spec:` present else `refine`. The cheap path #425 promised survives at `skills/dev/SKILL.md:17` Rule 4, keyed on a property of the work ("trivial change"), not on a type label.

**Transition table.** No `from_state="research"`, no `to_state="specify"` except a self-loop at `:437` — `specify` is entry-only and unskippable. Shortest legal path is `spec.approved-direct` (`:399-421`) then `implement.complete` (`:470-486`). `skip-specify`/`skip-review` config keys are documented but dormant; #380 commented them out of the shipped template.

**Timebox.** No mechanism exists — `NOT_FOUND(query=timebox|time-box|time box|deadline|time_limit, scope=skills/)`, `NOT_FOUND(query=timebox|time-box|time box|deadline|time_limit, scope=cortex_command/)`, `NOT_FOUND(query=timebox|time-box|time box|deadline|time_limit, scope=bin/)` — no ticket field, lifecycle field, config key, or CLI flag. Operators hand-wrote it anyway: #204's research and spec both say *"Time-box: single session."*

## Web & Documentation Research

**Enum governance.** Every governed tracker treats retiring a status as a **data-migration problem, not a schema edit** — Jira mechanically blocks deleting a status live items carry and forces per-(type, status) remapping first. Google Issue Tracker is fully closed; Azure DevOps caps at 32 states per type; GitHub capped org issue types at 25 in 2025. Practitioner guidance: cap at 6–9 statuses, push edge cases into **fields, not new statuses**. Documented anti-patterns: status sprawl, resolution chaos (`Done`/`Completed`/`Resolved`/`Fixed` simultaneously live — exactly `pixel-art-generator`'s failure), dead statuses.

**Human-in-the-loop modelling.** BPMN, Temporal, Airflow, and Camunda all had the opportunity to make "requires a human" a work-item *type* and each made it a **state or attribute** instead. This independently corroborates `backlog.md:102`.

**Spike practice.** A spike's Definition of Done differs *in kind* — about what got learned, not built — and spikes are deliberately **not estimated** (circular: the spike produces the estimate); you timebox instead, ending in an explicit proceed / pivot / invest-further decision.

**Against type proliferation.** A documented migration cites 8 issue types (including an "Improvement" indistinguishable from "Story") and 14 workflows as pure overhead with no offsetting behavior change.

## Domain & Prior Art

`/wayfinder` (`mattpocock/skills`, SKILL.md 11,900 B) charts only what can be stated precisely now and leaves the rest as unticketed fog; its tickets are *"a question to settle, not a slice of a build to execute."* It sits upstream of `to-spec` → `to-tickets`, which do the slicing.

**Three reasons its machinery does not transfer wholesale.** (1) Its own reception documents the seam failing: issue #689 reports the spec *"fails to capture the individual decisions, trade-offs, and explicit choices made during each round,"* causing implementation deviation — a defect our fused `research.md` structurally cannot have, since `## Decision Records` sits in the artifact `decompose.md:7` reads. (2) `to-spec` and `to-tickets` never mention wayfinder, map, or fog; the chain is a documentation convention, and #492 records `/to-spec` cannot be invoked programmatically at all. (3) `to-tickets` has a batch-approval gate that wayfinder itself lacks — our §5a already is that gate.

What transfers is the fog/ticket test (*"whether you can state the question precisely now — not whether you can answer it"*), the observation that resolution is *"a produced artifact plus an explicit handoff step, not a status flip"*, and — evaluated under `## Architecture` — the structural insight that an unwritten ticket cannot go stale.

## Architecture

### Pieces

- **Finished-work recognition** — closes the one named real-world failure by extending read-time normalization so a finished item cannot render as active in any repo, retroactively.
- **Parked-work visibility** — makes an item parked via the status field visible to the surfacing feature built for parked work, and stops it silently wedging its parent epic.
- **Vocabulary authority** — reduces the competing status/type declarations to one authoritative set and removes the decorative constants that read as the enforcement point but are referenced nowhere.
- **Epic closure truthfulness** — makes an epic's recorded outcome reflect its children's actual terminal values, makes a late-arriving child audible rather than silent, and makes closed epics visible to the epic map so the corpus can be measured at all.
- **Superseded-work prevention** — stops a downstream ticket being worked against an understanding a sibling has already invalidated, by structure rather than by anyone remembering; the mechanism is an open fork between interrupting the work and withholding its authorship.

### How they connect

Finished-work recognition and parked-work visibility are independent one-line-class fixes with no dependency on anything else; each closes a distinct observed failure. Vocabulary authority depends on both, because it narrows the terminal set and must not run before the values it would orphan are already normalized — the ordering is migrate-then-narrow, and the migration must bypass the write verb whose terminal cascade mutates unrelated items.

Epic closure truthfulness is independent of the vocabulary set, and it is where the other dependencies converge. Its visibility arm is the measurement instrument every deferred question rests on — until the epic map can see more than one epic, no claim about epics growing, decaying, or closing wrongly can be evidenced either way. Its late-child arm is a hard prerequisite for superseded-work prevention under **either** mechanism: whichever is chosen, the first wave's tickets going terminal is exactly what fires the parent-closing cascade, so without it every later wave is orphaned under a closed, silent parent.

Superseded-work prevention sits downstream of that closure work and is bounded by two existing decisions rather than by implementation cost. Interrupting the work is the cheaper arm and is compatible with both: downstream tickets carry `blocked-by` a reconciliation gate, the piece set stays complete so ADR-0007's grouping contract is untouched, tickets stay materialized up front so #196's revert condition is honored, and enforcement is already live at every selection surface — a blocked ticket is absent from ready lists, from triage recommendations, and from overnight eligibility, so it cannot be picked up until the gate is terminal. Its limit is that it guarantees a stop, not a rewrite; what happens at the gate is judgment. Withholding authorship is the stronger arm — an unwritten ticket cannot go stale, so decay becomes impossible by construction rather than interrupted — but it requires discovery to emit a deliberately incomplete piece set, which `decompose.md:9` currently classifies as a research defect and ADR-0007 governs, so it needs a successor decision; it also re-opens the axis #196 was reverted on, whose stated rationale (a hypothetical pain) no longer holds. The two arms are alternatives, not stages, and the evidence that would choose between them is the census the visibility arm makes possible.

## Decision Records

**DR-1 — No new ticket types; resolution mode is not a type.** `backlog.md:102` restricts routing to readiness with `idea` as the sole type-keyed exception, decided in #425 six days before this research. Four independent workflow systems model "requires a human" as a state or attribute rather than a type. `spike` is a genuine problem kind (same refine-through rate as `feature`); `epic` is a structural role that already occupies a type slot. Rejected alternative: excepting `backlog.md:102` for `decision`/`requirements` types — this would have argued against a fresh decision on weaker grounds than the one that established it, and the industry convergence points the other way.

**DR-2 — The investigation fast path is not evidenced; hold it.** Three claims were tested and all failed. *Cost*: controlling for tier and criticality, spikes are cheaper than comparable work — at complex/high, spike median 75,407 bytes (n=7) vs feature 103,974 (n=58) vs bug 80,417 (n=14). *Shape*: `specify.md` already offers a non-mechanical acceptance arm (c) `Interactive/session-dependent`, and #083 uses it correctly; #021's author chose the mechanical arm when the escape hatch was available. *Harm*: the two exemplars were correct outcomes — #021 retracted its own premise, found that the review phase never ran, and produced #043 which shipped; #374 is titled *"Build and ship the served next/advance lifecycle loop"* with its evidence gate *"waived by operator decision (go by fiat)"*, i.e. a build wearing a spike label. The terminal it would need already exists (`cortex-lifecycle-wontfix`). Rejected alternative: a third `dev` route keyed on investigation-ness — it would have routed #374 and #291, both builds, onto a research-only road, because the `type` field it keys on is itself unreliable.

**DR-3 — Staged emission was deferred on three grounds, then partially revived on a fourth.** The original deferral rested on: re-authoring already being available (DR-5), the ADR-0007 conflict, and the missing census. A fourth argument arrived at the Research→Decompose gate and none of those three tests touched it — that working a ticket against a superseded understanding is a **sequential-gate failure**, and this repo's own policy (`CLAUDE.md:29`, `docs/policies.md:11`) prefers structural separation over prose-only enforcement for exactly that class. That argument does not resolve the mechanism fork, but it does defeat the "just prompt for reconciliation" alternative, which is prose-only enforcement admitted only where deviation is cheap — and here the deviation is the reported failure. Accordingly the fifth piece is charted with both arms costed and neither chosen; the census is what decides.

**DR-4 — Requirements-in-feature-commits is a tuning question, not a gap.** The path is designed, tested, and deliberately biased toward firing. Any change here reverses a working mechanism and belongs in its own ticket with its own evidence.

**DR-5 — A body-write verb was considered and rejected; bodies are already editable.** `update_item.py` is frontmatter-only, but that boundary is correct by design: frontmatter needs ADR-0027's key-scoped quoting contract because a bare numeric-looking scalar type-leaks, whereas a body is free-form markdown for which the ordinary edit tool is the right instrument — a `--body-file` verb would wrap prose editing in a CLI for no validation benefit. Nothing blocks the direct edit, and re-authoring is in active use (`9af200e8`, `465c5acd`, `70ffcb69`, `f26c1392`; 232 of 425 tickets carry 2+ commits). Rejected alternative: shipping the verb anyway as the thing that prompts reconciliation — that is prose-only enforcement, and what remains open is structural, not instrumental.

## Open Questions

- **Which arm of superseded-work prevention, and on what evidence?** Interrupting (a `blocked-by` reconciliation gate, already enforced at every selection surface) guarantees a stop but not a rewrite; withholding authorship makes decay impossible by construction but needs an ADR-0007 successor and re-opens #196's axis. The census the visibility arm enables is the intended tiebreaker; what threshold in that census should decide has not been set.
- **Is the `completed` alias sufficient, or is a broader read-time normalization warranted?** Sibling repos carry `open`, `closed`, `resolved` — some already mapped, some not. The census across all consumer repos has not been run.
- **`deferred`: field or status?** Making `_is_deferred` consult `status` surfaces parked work, but leaves two mechanisms for one concept. Migrating the 10 items to `status: backlog` + `tags: [deferred]` collapses them — at the cost of a per-repo migration nothing here can reach.
- **How should an epic report a mixed-terminal outcome?** `:337` can derive the parent's status when children agree, but no vocabulary exists for "some complete, some wontfix." Scoping to the unanimous case discharges the defect without answering the question.
- **Should late-child detection warn or reopen?** Auto-reopen introduces a write that can undo a deliberate human close under concurrency; warn-and-record cannot repair the 39-day-old case in epic #9.
- **Does `cortex-lifecycle-wontfix` need a relabel or a sibling?** Its exit is correct for a successful investigation but its prose says "premise rejected." Contradiction surfaced between angles: one holds the label is the whole defect; another holds a distinct terminal event would be clearer. Unresolved.
- **What would revive the fast path?** ≥5 tickets at held tier that are genuinely bounded read-only investigations — not `investigate-and-<build-verb>`, not fiat-decided — with a nameable downstream harm. Across 425 tickets, one candidate for the first two conditions and zero for the third.
