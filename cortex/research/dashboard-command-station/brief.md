Discovery settled on a small, data-honest overhaul rather than a full command-center rebuild: three additions to the existing dashboard — a triage board (epic-grouped children plus a flat ready list, degrading to a plain list), a full-page ticket reader at /tickets/{id}, and a minimal archive-vs-active landscape strip — all fed by importing the same in-process backlog helpers the CLI already uses, held entirely in memory on the existing 30-second poll, never writing index.json.

Several bigger options were weighed and set aside. A headline landscape/kanban view with dependency graphs and volume metrics was rejected because the live backlog is nearly empty (3 open items, 0 open epics) against a huge settled corpus — that chrome would be dishonest at this scale. Regenerating index.json from the dashboard, adding an mtime gate, or writing a second YAML-parsing path were all rejected as write-boundary violations or duplicate logic. A slide-over ticket panel was deferred in favor of the simpler full-page reader. Sanitizing rendered markdown (nh3) was considered and rejected as an unneeded dependency given the existing trust boundary and loopback bind. Gating the whole epic on ticket #169 was dropped once research confirmed #169 already shipped its one-time archive sweep with no recurring mechanism — so the sweep-lag the landscape strip shows is a standing, structural condition, not a blocked prerequisite.

The accepted tradeoff: the board's data comes from helper functions that are label-poor by design — no titles, no readable blocked-reason text, tag-based deferral invisible to readiness — so the dashboard has to do its own in-memory joins to produce readable labels, adding real logic on top of "just import and render." Separately, the 30-second poll is synchronous and will briefly starve faster UI updates each cycle rather than being made async now.
