# Plan: triage-routes-ready-items-by-ticket

## Overview

Replace `_workflow()`'s type-first branch with a single readiness-driven `_recommendation()` consumed by both `render()`'s flat loop and `_render_epic_block()`, align the epic footer so it stops contradicting per-child `idea` rows, delegate the trivial-change cheap path to `skills/dev/SKILL.md` Step 3's existing rule-1 → rule-4 route, and stand up the first behavioral test coverage of `render()` — including a cross-block byte-identity guard parametrized over type-sensitive fixtures.

Key architectural decision: the shared function is the structural enforcement of #343's boundary (recommendation logic lives in the verb, not in prose). Requirement 3's guard is what keeps it honest — it compares the two blocks' *rendered output* against each other rather than against a recomputed expectation.

## Outline

**Stated divergence from the spec's phase assignment.** The spec assigns requirements 5 (`idea` branch preserved) and 6 (epic footer does not contradict per-child rows) to Phase 1, but both of their acceptance criteria are tests in `tests/test_triage_render.py`, which this plan creates in Task 3 under Phase 2. Phase 1 therefore lands the *behavior* for requirements 1, 2, 4, 5, and 6 — the `idea` branch and the footer partition both ship in Task 1 — while the *test acceptance* for 5 and 6 is consolidated into Phase 2's single test-authoring task. This is deliberate: `tests/test_triage_render.py` is one new module, and authoring it once by one implementer avoids splitting a single file across two tasks with a write-serialization edge. The cost is that requirements 5 and 6 have no executable check until Task 3 lands; Phase 1's Checkpoint below claims only what its own commands actually verify, and does not assert 5 or 6.

### Phase 1: Unify the recommendation (tasks: 1, 2)
**Goal**: One readiness-driven recommendation string serves both blocks, and the dev skill owns the trivial-change hatch. Behavior for requirements 1, 2, 4, 5, and 6 is complete at the end of this phase.
**Checkpoint**: `grep -c "direct implementation" cortex_command/backlog/triage.py` → `0`; `grep -c "cortex-core:build" cortex_command/backlog/triage.py` → `1`; `grep -c "route it from Step 1" skills/dev/SKILL.md` → `1`; `uv run pytest tests/test_dev_triage_refs_wired.py tests/test_build_epic_map.py -q` → `24 passed`. These four commands verify requirements 1, 2(a), 4, and 7 only. Requirements 5 and 6 ship as behavior in Task 1 but are **not** verified at this checkpoint — their tests do not exist until Task 3 creates `tests/test_triage_render.py` in Phase 2.

### Phase 2: Behavioral coverage (tasks: 3)
**Goal**: `render()` gains the behavioral coverage it never had, pinning the recommendation syntax, the cross-block drift guard, the ticket-425 regression, the known child-of-non-ready-epic hole, and the Phase-1 behavior for requirements 5 and 6 that Phase 1's checkpoint could not claim.
**Checkpoint**: `tests/test_triage_render.py` passes with the drift guard collecting exactly four parametrized cases over `bug`, `chore`, `idea`, `feature`, and with the requirement-5 and requirement-6 assertions green.

## Risks

- **Spec requirement 2 criterion (c) is unsatisfiable as literally written.** It asks that `inspect.getsource` of *both* `render` and `_render_epic_block` contain no `/cortex-core:` literal — but `_render_epic_block` keeps the `/cortex-core:discovery` empty-children line (`:113`) and the footer's `/cortex-core:refine` sentence (`:130`), both of which requirement 6 and the Non-Requirements explicitly preserve. Task 3 implements the tightened check described in its Context: zero `/cortex-core:` literals in `render`, and zero `/cortex-core:build` plus zero retired mark literals in `_render_epic_block`. That still pins the actual claim — no per-item recommendation is computed inline — while leaving the footer and empty-children sentences where the spec puts them. Satisfying the literal version would require hoisting the footer into its own helper, which the spec's Non-Requirements rule out.
- **Renaming `_workflow` → `_recommendation` is a deliberate call, not forced.** Requirement 7 leaves it optional. Renaming costs one line in `tests/test_dev_triage_refs_wired.py:101`, bundled into Task 1 so no commit leaves the suite red; keeping the old name would leave a symbol named after the type-routing concept the change deletes.
- **Task 1 and Task 2 share a level despite the mixed-complexity guidance.** They touch disjoint files with no shared symbol, and in a three-task graph forcing a separate wave would only add depth. If Task 2 lands first, rows still say "direct implementation" while the skill re-routes picked items — a transiently redundant state, not a broken one.
- **Task 3's byte-identity guard is the whole defense against silent re-drift.** If it is weakened to a substring check or its fixtures collapse to `feature`, the boundary this change installs stops being enforced and only the prose in the module docstring holds it. Task 3's Verification checks 2 and 3 exist precisely because the guard otherwise verifies only itself.
- **Two known bugs are pinned rather than fixed** (per the spec's Non-Requirements): `_is_refined()` still trusts frontmatter with no on-disk spec check — now extended to `bug`/`chore` for the first time — and a ready child of a non-ready epic still vanishes from output entirely. Each needs its own ticket.
