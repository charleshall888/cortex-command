# Specification: reconcile-dashboard-docs-and-observability-requirements

> Epic context: parent epic #410's discovery research lives at `cortex/research/dashboard-command-station/research.md`. It is background spanning all five children and is not reproduced here; this ticket's own research is `cortex/lifecycle/reconcile-dashboard-docs-and-observability-requirements/research.md`.

## Problem Statement

Seven places in this repo state how the dashboard binds to the network, and the two that are correct are the two nobody cites. `cortex/requirements/observability.md:107` declares that the dashboard "binds to all network interfaces (`0.0.0.0`) … by design", `cortex/requirements/pipeline.md:156` repeats it while also delegating to that same doc, and `docs/overnight-operations.md:627` builds a threat model on it — but the shipped verb `cortex dashboard` has always bound `127.0.0.1` (`cli.py:498-503`). Only the contributor recipe `just dashboard` binds `0.0.0.0`, and it serves an already-unsanitized markdown surface: `data.py:940-942` renders `morning-report.md` through `markdown.markdown(...)` and `session_detail.html:56` emits it with `| safe`, with no Host-header or Origin validation anywhere in the package. Sibling ticket #413 is about to add a second unsanitized renderer justified explicitly by "contingent on the loopback bind". This ticket makes the claim true on every launch path, closes the one path that contradicts it, and removes the duplication that produced the drift twice — once on 2026-04-03 (`cortex/lifecycle/archive/gather-area-requirements-docs-for-four-missing-areas/review.md:27,82`, where the same two docs disagreed in the opposite direction) and again today.

## Phases

- **Phase 1: Bind truth** — make every bind claim true by collapsing seven copies to two, and give the one non-loopback launch path a loopback default with an explicit opt-in. Safety information is **relocated, never dropped**.
- **Phase 2: Ownership and regather** — declare a dashboard-docs owner, route real traffic to it, and bring `observability.md`'s Dashboard entry and `docs/dashboard.md` back in line with shipped behavior.

Priority key: a requirement is **must-have** when its claim is false the moment `just dashboard` flips, when it preserves safety information this ticket would otherwise delete, or when a later requirement in this spec depends on it. Accuracy repairs to `observability.md` / `docs/dashboard.md` that are wrong today but harm nobody are **should-have**. Low-consequence corrections are **nice-to-have**.

**Check-authoring rule (binding on every requirement below).** Acceptance greps are content assertions, not line pins, and every ban is paired with a positive assertion. Three failure modes are forbidden because this spec previously committed all three: (a) a whole-file `grep -c` used where only one of several occurrences is being edited; (b) a line number (`:159`) used as a check address when another requirement inserts lines above it; (c) a `returns 0` deletion check with nothing asserting the replacement exists. Where a check would need a line address, address it by enclosing section heading and substring instead.

## Non-Requirements

- **No `cortex dashboard --host` flag.** Considered and rejected during critical review. `cortex_command/cli.py:498` is the package's only `uvicorn.run` callsite and hardcodes loopback; `pyproject.toml:137` ships `packages = ["cortex_command"]` with no justfile, so no wheel-only consumer has ever been able to bind a non-loopback interface. Adding the flag would expand the exposed population inside a ticket whose purpose is closing exposure, ship an unguarded network-exposure surface to every install, and — since `cortex_command/lint/contract.py:461`'s `_BINARY_RE` cannot see `cortex <verb> --flag` — carry no gate against future doc/flag drift. R10 documents `ssh -L` over the existing Tailscale mesh as the supported remote path instead, at zero new shipped surface. The `--port` help text at `cli.py:1228` ("TCP port to bind on 127.0.0.1") stays true and needs no edit.
- **No markdown sanitizer.** Epic #410's research adjudicated this (`cortex/research/dashboard-command-station/research.md:85`); this ticket does not reopen it.
- **No `TrustedHostMiddleware` or Origin validation.** Confirmed absent and confirmed to close the residual DNS-rebinding risk, but "add security middleware" is a different job with its own evidence bar. Deferred to a follow-up ticket; see Technical Constraints for how the residual is recorded instead.
- **No bind-address drift gate, and no bind assertion folded into `test_routes_smoke.py`.** `cortex/requirements/project.md:41` retired `bin/cortex-requirements-parity-audit` (commit `e3aef4e5`) for this class even though it was informational and never failed. R6/R8/R11/R14 collapse the duplication that caused the drift, which is the structural fix — post-collapse the fact lives in one place, and a gate defending a single copy earns less than it costs.
- **No documentation obligation added to any sibling ticket body.** R12 plus R13 make the ownership rule reachable, which is the mechanism; a ticket-body Edges bullet is not, because a build reads its spec. Specifically: #412's spec (`cortex/lifecycle/add-the-triage-board-panel-and/spec.md:76`) already declares "No edits to ... `docs/dashboard.md`", so a body edit would contradict an approved sibling artifact it cannot reach. #411 is `status: in_progress` and adds no panel (its spec's Non-Requirements: "No board, reader, or landscape views"). #414's spec already declares `docs/dashboard.md` MODIFIED, so it is editing the owned doc under R12's rule regardless.

## Edge Cases

- **Empty `DASHBOARD_HOST`**: `DASHBOARD_HOST= just dashboard` — `env_var_or_default` returns set-but-empty, so an unquoted `--host {{dashboard_host}}` would hand uvicorn `--host --port 8080` and misparse. R1's quoting requirement covers this; the recipe must not silently launch on an unintended interface.
- **`just --dry-run` expands only just-level interpolations**: any host-rendering conditional written in the recipe *body* leaves `$DISPLAY_HOST` unexpanded, so R2's checks would fail on a correct-looking implementation. This is why R1 mandates the second top-level `dashboard_display_host` variable rather than a shell conditional.
- **Contributor who relied on LAN access**: after R1, `just dashboard` no longer serves the LAN. The opt-in is documented in the same change (R9), and R10 documents the port-forward path for anyone who needs off-host viewing.
- **`#412`'s spec asserts a sequencing that no longer holds**: it says "#415 owns the regather and is sequenced after this ticket." Under this spec #415 runs first. This is harmless rather than contradictory — R15 removes `observability.md`'s panel enumeration outright, so #412's panels create no obligation in the file it was deferring to. No edit to #412 is required; the stale sentence is recorded here so a reviewer does not read it as an unmet dependency.
- **Sibling tickets edit the same files concurrently**: #414's spec declares `docs/dashboard.md` and `justfile` MODIFIED, and #411 is `in_progress`. Every check in this spec is content-addressed rather than line-addressed specifically so concurrent insertions above a target do not invalidate it.
- **`lifecycle.config.md`'s demo command**: `demo-commands` names `just dashboard`. A loopback bind still serves a local demo, so no change is needed.
- **A `0.0.0.0` string legitimately appears elsewhere**: `cortex/backlog/047-*.md:26` and `056-*.md:48` discuss `WebFetch(domain:0.0.0.0)` deny-list entries. R11's grep is scoped to `cortex/requirements/` and `docs/` and must not sweep these up.
- **Archived audit artifacts**: `cortex/lifecycle/requirements-skill-v2/area-audit.md:71-83` records the 2026-04 audit that validated the docstring against the requirements doc — the two reinforcing each other's error. It is history and is not edited.

## Technical Constraints

- **The loopback bind is defense-in-depth, not a sanitizer substitute.** Verified: no `TrustedHost`, `CORS`, `Origin`, or `add_middleware` anywhere in `cortex_command/dashboard/`. DNS rebinding reaches a loopback-bound service that does not validate the Host header (webpack-dev-server's CVE-2018-14732 was fixed with a Host check, not a bind change). "0.0.0.0 Day" (Oligo, Aug 2024) reaches services bound to `0.0.0.0` specifically and is closed by R1 — but the residual rebinding risk against an unauthenticated local service remains and is accepted here, not discharged. Documentation produced by this ticket must not describe the loopback bind as satisfying #413's sanitizer precondition. Do not cite "CVE-2024-3566" for 0.0.0.0 Day — that ID is an unrelated Node.js/Windows `cmd.exe` argument-injection issue.
