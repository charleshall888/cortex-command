## Codebase Analysis

**The reservation, and every hardcode of it.** `_get_next_id` excludes 990–999 from its `max(ids)` scan (`cortex_command/backlog/create_item.py:38-47`), commented "reserved for dashboard-seed fixtures". The complete enforcement/duplication set: the predicate itself (`create_item.py:44`); `_BACKLOG_ITEMS`' literal IDs 990–994 (`seed.py:1011-1015`); `clean_all`'s `range(990, 995)` (`seed.py:1223`); **a second, independent hardcode of 990–992** as `backlog_id` values in `write_pipeline_fixtures` (`seed.py:313,319,325`) that references `create_item.py` not at all; and three pinning assertions in `tests/test_create_backlog_item.py:27-40`. Nothing in `skills/`, `plugins/`, `justfile`, or docs hardcodes it. #231's spec recorded the Non-Requirement "No module-level reservation constants… If the predicate ever gets a second consumer, promote to a named constant then — not now" (`cortex/lifecycle/fix-get-next-id-in-cortex/spec.md:29`) — `seed.py:313` is already that second consumer, silently drifted.

**The allocator has a permanent ceiling, not a boundary hole.** Because 990–999 are excluded from `max(ids)` unconditionally, `max(ids)` can never exceed 989, so `_get_next_id` can never return anything above 990. Reproduced empirically: with only `989-real.md` present, four consecutive allocations returned `990`, `990`, `990`, `990`, producing four distinct files all carrying ID 990 (`atomic_write` never collides because the slug differs, so nothing errors). This is reachable through the ordinary shipped `cortex-create-backlog-item` verb, not just hand-numbering. Prior art in-repo called this "latent and distant" (`cortex/lifecycle/add-the-dashboard-ticket-feed-with/research.md:64`); it is better described as a dated ceiling — see Consumer-Repo Impact.

**Duplicate IDs resolve arbitrarily and silently.** No dedup exists in `generate_index.py`; `readiness.py:76-84` builds its id→status lookup as a plain dict (last-write-wins, so whichever filename sorts later silently wins blocker resolution); `collect_items` accumulates `active_ids` as a `set[int]` (`generate_index.py:128,158`); #411's snapshot `items` is an id-keyed dict by pinned schema. Nothing raises, nothing logs.

**`_get_next_id` globs non-recursively**, so `cortex/backlog/archive/` IDs are invisible and archived IDs get reallocated. Latent today — `cortex/backlog/archive/` does not exist in this repo — but the fixture set proposed below introduces an archived fixture, which makes it live.

**Seed backlog items and seed lifecycle dirs are structurally unlinked today.** `write_backlog_items` (`seed.py:1029-1073`) never emits `lifecycle_slug`, and `collect_items` falls back to `slugify(title)` (`generate_index.py:164`). Verified: `slugify("Seed: Add authentication to API gateway")` → `seed-add-authentication-to-api-gateway`, which is not `seed-feature-alpha`. So `lc_dir.is_dir()` is false (`generate_index.py:176`), `lifecycle_phase` falls through to an absent frontmatter key, and `phase` is `None` for every seed item.

**The writer emits 8 of the 21 fields `collect_items` can populate** (`seed.py:1053-1064`): `schema_version, uuid, title, status, priority, type, tags, created, updated`. Never emitted: `areas, blocks, blocked-by, parent, research, spec, discovery_source, plan, lifecycle_slug, session_id, lifecycle_phase, repo` — i.e. every field the snapshot's `epics`, `blocked_why`, and lifecycle-linking logic depend on. `_BACKLOG_ITEMS` is a fixed 6-tuple rendered by one hard-coded f-string, so optional fields require restructuring both the table and the writer, not extending them.

**Writer/cleaner symmetry is uneven by design.** `clean_all` steps 1–2 verify a content marker before deleting (`seed.py:1163-1193`); steps 3–4 `shutil.rmtree` over globs with no content check (`:1196-1204`); steps 5–7 `unlink()` unconditionally (`:1206-1219`); step 8 globs `{990..994}-seed-*.md` blind (`:1221-1227`). Every writer's output has *some* removal step — nothing is orphaned by omission — but three categories are content-blind.

**`seed.py` has no test file.** Repo-wide grep for `dashboard.seed`/`dashboard/seed` finds no importer but `create_item.py`'s comment. `write_all`/`clean_all` have zero automated coverage.

**No existing writer produces `research.md`/`spec.md`/`review.md`.** `plan.md` is the only prose-adjacent artifact and is deliberately checkbox-only (`seed.py:576-583`). The established per-feature shape is `(repo_root, slug, status)` → `feature_dir.mkdir(parents=True, exist_ok=True)` → `write_text(..., encoding="utf-8")` → a `print` confirmation, with per-feature variance driven by small slug-keyed lookup dicts (`_FEATURE_TIER`, `_FEATURE_ESCALATIONS`, etc.).

## Web & Documentation Research

**In-domain sentinel values are a named anti-pattern.** Abseil Tip 171 states the core problem: a sentinel "remains within the type's valid domain, so compilers can't force acknowledgment," it is ambiguous across systems, and it blocks evolution "if that special value becomes legitimately needed later" (https://abseil.io/tips/171). PEP 661 makes the same argument for Python (https://peps.python.org/pep-0661/). Both are established engineering guidance, not blog opinion, and both indict "reserve 990–999 out of the numeric ID space" directly.

**The robust contrasting shape is a self-describing name reserved out-of-band from the numbering system.** RFC 2606 reserves `.test`, `.example`, `.invalid`, `.localhost` as whole namespace segments, with a rationale that generalizes exactly: "Test and experimental software can escape and end up being run against the global operational DNS. Even examples used 'only' in documentation can end up being coded and released or cause conflicts due to later real use" (https://datatracker.ietf.org/doc/html/rfc2606, later folded into RFC 6761).

**Reserved numeric ranges fail by exhaustion and by boundary confusion.** The ephemeral-port history is the cleanest documented case — Windows defaulted to 1025–5000, Linux to 32768–49151, both conflicting with IANA's registered range until Microsoft moved to comply (https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting). RFC 1918 overlap on acquisition is the canonical "reserved block, still collides" case (https://aws.amazon.com/blogs/networking-and-content-delivery/connecting-networks-with-overlapping-ip-ranges/). ID reuse after deletion is the security-relevant instance of the same family — CVE-2024-43784 in lakeFS, where a new user with a deleted user's name "will inherit all of the previous user's credentials" (https://api.osv.dev/v1/vulns/CVE-2024-43784). HTTP status ranges are the counterexample worth naming for balance, and they work because they are centrally governed with generous per-category headroom — not a ten-slot block carved from the tail of an ungoverned growing sequence.

**Teardown symmetry comes from ownership, not pattern-matching.** pytest's `tmp_path` is the canonical pattern: the fixture owns a unique fresh location, and "the directory and all contents are removed even if the test fails" (https://docs.pytest.org/en/stable/how-to/tmp_path.html). Rails enforces the adjacent rule with `ActiveRecord::ProtectedEnvironmentError`, refusing destructive action against a production-flagged database unless an explicit env var overrides — an opt-in escape hatch, not an opt-out default (https://github.com/rails/rails/issues/53059). Direct case studies of *seed teardown* destroying production data were not found; the nearest documented incidents (GitLab 2017) are general destructive-script postmortems, so this supports the hazard class rather than an on-point precedent.

**Commingled-and-unmarked demo data has no prior art.** Every in-namespace mechanism found carries a self-describing marker: WordPress's fixed `hello-world` slug, Jira's distinctly-named "Sample Scrum Project" (https://support.atlassian.com/jira/kb/create-a-jira-cloud-board-with-sample-data/), Stripe's and Linear's type-prefixed IDs (https://linear.app/docs/editing-issues). Products with a genuine separate store use it — Stripe test mode is "a fully separate environment… API objects in one mode aren't accessible to the other" (https://docs.stripe.com/api/customers/object); Plaid's sandbox warns "all data in the Sandbox are assumed to be fake" (https://plaid.com/docs/sandbox/). Self-identification and filtering are distinct mechanisms; only the latter was ruled out by #411.

**Demo-data design favors state coverage over plausibility.** Storybook's stated rationale for mock data is to "simulate hard-to-reach states (empty, loading, etc)" (https://storybook.js.org/blog/storybook-addons-to-manage-data-state/); Faker ecosystem guidance is explicit that "realism does not create coverage" and boundary/invalid cases should be deterministic. This bears directly on the deliberately-dangling-artifact question below.

## Tradeoffs & Alternatives

- **A. Filename token** (`*-seed-*`) — free (filename-only, matching the allocator's existing shape) but **demonstrably unsafe as a sole discriminant**: this ticket's own file, `414-enrich-dashboard-seed-fixtures-with-board-and-reader-shaped-variety.md`, contains `-seed-`. Worse, a real feature titled "Seed feature flags system" slugifies to `cortex/lifecycle/seed-feature-flags-system/`, which today's `clean_all` glob already `rmtree`s in full — a live latent bug, not a hypothetical one. A narrower enum token hardcodes the fixture roster in two files that must stay hand-synced, and breaks the moment the set grows, which is this ticket.
- **B. Tag** (`dashboard-seed`, already written but never read) — forces frontmatter parsing on every ID allocation (a real cost the current filename regex doesn't pay) via one of the repo's several independent parsers, and covers only backlog `.md` — nothing about the other seven cleanup categories.
- **C. High-offset block** — same machinery, bigger arbitrary boundary; predicts corpus growth rather than establishing a fact, and ADR-0010 already rejected integer-space encoding as "a leaky encoding that hides identity behind a scaling trick."
- **D. Separate directory** — `collect_items` globs non-recursively, so every reader must learn a second location; #231 already rejected this as "audit of every backlog reader."
- **E. Separate repo root** — achievable today via `CORTEX_REPO_ROOT` with zero code change; rejected by the Tradeoffs angle as defeating the seeder's purpose of populating the *real* dashboard. The adversarial pass disputes that rejection — see below.
- **F. Manifest** — persist what creation made; deletion becomes a table lookup. Recommended by the Tradeoffs angle on the basis that `write_all` already assembles `written_paths`. **That basis is false** — see Adversarial Review §2.

## Adversarial Review

The core wave shared one framing — *read-side pollution*, the dashboard showing fake tickets. The verified damage is **write-side**. None of options A–F address it, including the recommended F.

**1. The seeder clobbers live canonical state, so "delete what you created" is the wrong operation.** `seed.py:181-187` resolves `cortex/lifecycle/overnight-state.json`, unlinks it, and `shutil.copy2` a regular file over it. `overnight/plan.py:588-592` maintains that exact path as a **symlink** to the active session's state (the single-active-session pointer). The seeder destroys it deliberately (its own comment: "must be a regular file, not a symlink"), and `clean_all` step 1 deletes the seed file **without restoring the symlink**. Same shape for `overnight-events.log`, `pipeline-state.json`, `pipeline-events.log`, `metrics.json` — unconditional writes over live paths, no backup, no marker check inbound. The `tmp_path` analogy fails: `tmp_path` owns a fresh exclusive directory; this is closer to a test writing into `~/.bashrc`.

**2. `written_paths` is not complete, and two writers ignore their caller's root.** `write_all` appends paths *by hand* in parallel to the writers (`seed.py:1090-1130`), omitting the feature directories themselves, `exit-reports/`, `learnings/`, and the session dir; a future writer that forgets to append leaves an orphan a manifest can never reach. Separately — and this is the sharper point — `write_overnight_state` and `write_overnight_events` take `session_dir`, not a repo root, and independently call `_resolve_user_project_root()` for their canonical copies (`seed.py:181`, `:282`). So `write_all(tmp_path, …)` writes session files under `tmp_path` **while clobbering the canonical files in the developer's real repo**. (The adversarial phrasing "discards the `repo_root` argument" is imprecise — these two never receive one — but the effect is exactly as described.) This is a hard blocker on the ticket's own stated remedy: the first naive `write_all(tmp_path, …)` test corrupts tracked repo files.

**3. Seeding installs a fake session that a background launchd daemon will try to recover.** Verified chain: the seeder writes `"phase": "executing"` (`seed.py:166`) and no `runner.pid`; `guardian.py:49-62` enumerates every non-symlink `sessions/*` dir holding an `overnight-state.json`; `recovery.py:77-79` returns True iff phase is `executing` and the runner pid is not live, with an absent pid file explicitly qualifying; `scheduler/macos.py:102-108` installs a persistent per-host launchd agent firing `cortex overnight guardian scan` on a timer. A seeded fixture is a standing unattended recovery target. This reframes the ticket — the hazard is not "the board shows fake tickets," it is "the seeder writes state autonomous machinery acts on" — and it kills "treat a missing manifest as nothing-to-clean," because the orphan is not inert.

**4. Verified: this repo already has committed seed output.** `git ls-files` shows `cortex/lifecycle/overnight-events.log` and `cortex/lifecycle/pipeline-state.json` are **tracked**, and both carry seed content — `"name": "seed-pipeline-feature-one"` / `"backlog_id": "990"`, and a first line with `"session_id": "overnight-seed-2026-05-18-1424"` (committed in `9323efea`). Seed fixtures have already escaped into git history, which removes the "at least they're untracked" comfort the corpus survey implied. Corollary: `cortex-dashboard-seed --clean` on a never-seeded repo **deletes tracked files**, because steps 5–7 unlink unconditionally.

**5. Manifest failure modes the recommendation does not survive.** Where does it live? `cortex/lifecycle/` is tracked (§4), so a manifest there gets committed and travels to clones describing files that don't exist; a gitignored location dies to `git clean -fdx`, which this repo's worktree flows use. Worktrees each have their own `cortex/`, and `CORTEX_REPO_ROOT` is set differently by different callers, so seed-in-main / clean-in-worktree resolve to different roots. Per §2 a manifest rooted at X literally cannot describe the canonical files written elsewhere. Seeding twice without cleaning overwrites the first manifest — benign only while IDs are deterministic, which de-reservation would end. A crash between last file and manifest persistence orphans everything; writing the manifest first inverts this to over-claiming. Its one genuine advantage stands: it is the only option that survives a wheel upgrade changing what the seeder writes.

**6. Two corrections to the adversarial pass itself.**
- Its `counts.archived` finding conflates two different surfaces. #411's snapshot `counts` derives from `collect_items`' `active_ids`/`archive_ids` (spec R3/R4), which *do* read `cortex/backlog/archive/` (`generate_index.py:117-127`) — so the proposed archive fixture is correct for the snapshot. The non-recursive, status-keyed `counts` at `data.py:988,1023` is the *existing* distribution bar, a separate surface this ticket does not feed. (Noted in passing: #411's R4 acceptance text says `cortex/lifecycle/archive/` where the code reads the backlog archive — a wording slip in #411, not this ticket's to fix.)
- Its claim that `write_all` "discards the `repo_root` argument" is imprecise, as corrected in §2. The defect is real; the mechanism is that the two writers never take a root at all.

Standing points not otherwise placed: `cortex/backlog/archive/` does not exist in this repo, so the archive fixture requires the seeder to `mkdir` into a consumer's tree with no matching cleaner step; and `build_epic_map` raises `SchemaVersionError` on `schema_version != "1"` (`build_epic_map.py:126-133`), a hard-fail path the new epic fixture flows through (#411's R9 already requires `strict_schema=False` at its own call site).

## Open Questions

- **Does this remain one ticket?** — **Resolved (operator, 2026-07-27): one ticket.** The adversarial pass argued for three (allocator correctness / seed containment / fixture enrichment), on the mechanical grounds that #414 cannot test `seed.py` until the root divergence (§2) is fixed, plus the blast-radius asymmetry of allocator changes riding a chore ticket. The operator kept it whole. The containment decision below substantially reduces the force of the split argument: with fixtures out of the real backlog, the allocator half collapses to deleting a predicate rather than replacing a mechanism, and the testability blocker is resolved inside the same change. Spec must still phase the work so the allocator change is independently reviewable.
- **May the seeder write canonical live paths at all?** — **Resolved (operator, 2026-07-27): no — contain seeding to an isolated root.** Seed and serve from a throwaway root rather than the user's real `cortex/` tree. Verified achievable today with zero code change: `cli.py:498-503` runs uvicorn **in-process**, so the dashboard inherits the caller's environment, and `app.py:_root()` resolves per-request through `_resolve_user_project_root()`, which reads `CORTEX_REPO_ROOT` first (`common.py:87-89`).
