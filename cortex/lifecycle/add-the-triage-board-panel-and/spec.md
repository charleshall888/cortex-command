# Specification: add-the-triage-board-panel-and

> Epic reference: `cortex/research/dashboard-command-station/research.md` (parent #410) — background only, scoped to this ticket. Ticket-level research: `cortex/lifecycle/add-the-triage-board-panel-and/research.md`.

## Problem Statement

Deciding what to pick up means re-running `/cortex-core:dev`'s triage inside a token-metered session every time it is consulted, and the dashboard's only backlog surface is an aggregate distribution bar with no rows — so ready-vs-blocked-vs-deferred state and epic structure are invisible at a glance. This makes that picture persistent and zero-token by rendering the ticket-feed snapshot #411 shipped.

**The landscape strip originally bundled into this ticket is dropped** (see Non-Requirements). Its evidence did not survive review: the morning-report noise it cited was fixed at the consumer, the archive it reported against is largely residue from a documented `--dry-run` incident, archiving is not standing down, and #306's revival clause requires the settled-corpus question be reconsidered jointly with an archive verb rather than split from it. This ticket is the board.

#411 landed during this refine (`731b46de`), so its snapshot is real code, not a contract to transcribe. Every requirement below is written against the shipped `cortex_command/dashboard/ticket_feed.py`, and R3 makes rendering against its actual output a test obligation rather than a schema assertion — the earlier draft of this spec asserted against a hand-transcription and misread the epics envelope, the child-id type, and the row set as a result.

## Phases

- **Phase 1: Triage board panel** — the panel, its data joins, badge vocabulary, and tests.
- **Phase 2: Ticket record reconciliation** — correct #412's own falsified body claims and record the dropped strip. No code; no dependency either direction.

## Requirements

1. **A `/partials/triage-board` route and panel exist and are smoke-tested**: a route in `cortex_command/dashboard/app.py` following the existing `@app.get("/partials/<name>")` shape, a fragment template `templates/triage_board.html` with no `<section>` wrapper, and a `<section id="triage-board" hx-get="/partials/triage-board" hx-trigger="load, every 30s" hx-swap="morph">` registration in `base.html`. Acceptance: `"/partials/triage-board"` appears in `PARTIAL_ROUTES` (`cortex_command/dashboard/tests/test_routes_smoke.py`) and `pytest cortex_command/dashboard/tests/test_routes_smoke.py` exits 0. **Phase**: Triage board panel

2. **The section is appended as `§ 11` and its label is emitted twice**: once as a placeholder in the `base.html` shell and once as the partial's own first line, because `hx-swap="morph"` replaces the section's inner content on first `load` and a single-site label disappears after it. No existing section is renumbered. Acceptance: the multiset of `§ NN` labels found across `cortex_command/dashboard/templates/` equals its pre-change value plus exactly two occurrences of `§ 11`, one in `base.html` and one in `triage_board.html`. **Phase**: Triage board panel

3. **Board tests render against the real feed, never a hand-written snapshot dict**: at least one template test builds its input by calling `cortex_command.dashboard.ticket_feed.build_backlog_snapshot` over a fixture corpus on disk, so a future change to the feed's shape fails this ticket's tests rather than silently rendering blanks. Hand-built dicts may supplement but not replace it. Acceptance: `grep -c 'build_backlog_snapshot' cortex_command/dashboard/tests/test_templates.py` ≥ 1, and that test asserts on rendered row content (not merely that rendering did not raise). **Phase**: Triage board panel

4. **Every active item reaches a row.** The board's row set is `snapshot["item_order"]` — the feed's priority-then-id ordering over all active items — not `ready` alone. `ready` and `ineligible` classify rows; they do not select them. Verified against the live corpus: `ineligible` currently carries `{"id": "156", "reason": "status: deferred", "kind": "status"}` and the same for `295`, and both items are absent from `ready` and from every epic's children, so a `ready`-only board would drop them along with the `deferred_status` flag meant to badge them. Acceptance: rendering a fixture whose snapshot has a non-empty `ineligible` produces a row for every id in `item_order`, including each `ineligible` id, and each such row displays its `reason`. **Phase**: Triage board panel

5. **The epic map is read at `snapshot["epics"]["epics"]`**, not `snapshot["epics"]`. `build_epic_map` returns a two-key envelope `{"schema_version", "epics"}` (`build_epic_map.py:173`), so iterating the outer dict yields the literal keys `schema_version` and `epics` and zero epic ids. Acceptance: a fixture with exactly one epic renders exactly one epic section, and no rendered section is titled or keyed `schema_version`. **Phase**: Triage board panel

6. **Child ids are stringified before joining `items`**: child records carry `id` as `int` (`411`) while `snapshot["items"]` is `str`-keyed (`'411'`), so an unconverted lookup yields Jinja `Undefined` and renders blank rather than raising. Acceptance: a fixture epic with ≥1 child renders that child's title and status text, and the assertion is on the visible text, not on absence of an exception. **Phase**: Triage board panel

7. **Per-row fields come from `items`, never from child records**: child records carry only `{id, spec, status, title}` (`build_epic_map.py:158-163`), so priority, type, `phase`, `deferred_status`, and `deferred_tag` are unavailable there. Every row — epic-parented or flat — resolves its display fields through `snapshot["items"][str(id)]`. Note the item record carries both `lifecycle_phase` (raw, still `"none"` for some items) and `phase` (null-normalized); rows read `phase`. Acceptance: an epic child carrying `priority: high` and `tags: [deferred]` renders both its priority and its deferral flag — neither of which exists on the child record; and a fixture item with `lifecycle_phase: none` renders no phase text while a fixture item with `lifecycle_phase: implement` renders `implement`. **Phase**: Triage board panel

8. **Grouping is presence-based, with no count threshold**: one section per epic id present in the epic map, listing that epic's children; every `item_order` id that is not any epic's child renders in one flat list below. No item-count or epic-count comparison selects between layouts. Rationale: 45% of `wild-light`'s active non-epic items have no epic parent, so the flat list is a primary view at scale, not a small-set fallback. Acceptance: rendering a 1-epic fixture and a 6-epic fixture produces the same structural shape — one section per epic plus one flat list — differing only in repetition count; and no template expression compares a collection's length to a numeric literal (`grep -cE '\| *(length|count) *[<>]=? *[0-9]'` = 0 over `triage_board.html`, the idiom actually reachable in Jinja, since `len(...)` is unbound in this environment). **Phase**: Triage board panel

9. **Backlog statuses map to existing `badge-*` classes through a template-local dict**: the board defines its own status→class map and calls `badge(css_class=…, label=…)`. It must map to class names (`badge-red`, `badge-amber`, `badge-gray`, `badge-green`, `badge-blue`, `badge-purple`, defined at `base.html:642-680`) — **not** to `backlog_panel.html:2-17`'s values, which are CSS custom properties (`var(--c-state-failed)`) consumed as `style="--c: …"` on `.tint-c` spans and would emit `class="badge var(--c-state-failed)"`, matching no rule. It must not call `badge(status=…)`, whose `_BADGE_CLASS_MAP` (`app.py:82-93`) is the feature/run-outcome vocabulary. Acceptance: every badge in the rendered output carries a class matching `^badge-(red|amber|gray|green|blue|purple)$`, and none contains the substring `var(--`. **Phase**: Triage board panel

10. **Unrecognized status, type, and priority values render verbatim**: all three vocabularies are open in practice (`create_item.py` applies no `choices=`), and `status: deferred` — live on 2 items here and 8 in `wild-light` — appears in no documented enum, in neither `TERMINAL_STATUSES` nor `_STATUS_MAP`. The board follows the existing raw-passthrough precedent (`generate_index.py:176-184`) rather than blanking or failing. Acceptance: a fixture carrying `status: needs-triage`, `type: architecture`, and `priority: contingent` renders all three strings visibly with a fallback badge class and no raised exception. **Phase**: Triage board panel

11. **Blocked state comes from `blocked_why` / `ineligible`, not from truthy `blocked_by`**: `triage.py:96-97` badges blocked whenever `blocked_by` is non-empty without checking the blocker is unresolved, which is over-inclusive since blockers pointing only at terminal items resolve silently (`readiness.py:152-157`). Rows render `blocked_why`'s resolved entries as text — `#<ref> (<status>)`, since `title` is frequently `null` in live data. Acceptance: a fixture item whose `blocked_by` names only a `status: complete` item renders **not** blocked; a fixture item blocked by a non-terminal item renders blocked and displays that blocker's id and status. **Phase**: Triage board panel

12. **The two backlog deferral flags render distinctly from each other and from the run-outcome vocabulary**: `deferred_status` and `deferred_tag` are independent — a tag-deferred item at an eligible status legitimately appears in `ready`. `deferred_status` renders as a status badge; `deferred_tag` renders as a non-badge text flag under a class prefix that is not `badge-`, so neither can be confused with `alerts.py:81`'s unrelated overnight-run `deferred`. Acceptance: a fixture with `status: backlog` + `tags: [deferred]` appears in the ready set, shows the tag flag, shows no status badge reading `deferred`, and its markup contains no `badge-amber`. **Phase**: Triage board panel

13. **Rows are non-navigational disclosures with ticket-derived ids**: rows render as `<details>`/`<summary>` following `feature_cards.html:50-101`, each carrying `id="ticket-{{ id }}"` so `base.html:2219-2257`'s `sessionStorage` restore — which keys on `d.id` — reattaches to the same ticket across morphs. An index-derived id is not acceptable: `item_order` re-sorts on any priority or status change, so positional ids would reopen the wrong rows. No row carries a navigation affordance of any kind — not `href`, not `hx-get`, not `hx-push-url`, not `onclick` — because the `/tickets/{id}` reader is #413 and `feature_cards.html:226-228`'s live `href="#"` placeholders are the exact defect epic #410's Why cites. Acceptance, both conjuncts: rendering a fixture containing ticket `412` produces `id="ticket-412"`, and re-rendering with `item_order` reversed still produces `id="ticket-412"` for that row; and no rendered row element carries `href`, `hx-get`, `hx-push-url`, or `onclick`. **Phase**: Triage board panel

14. **Never-polled, polled-and-empty, and stale are three distinct renders**: `backlog_snapshot is None` renders a loading state matching the existing placeholder idiom (`base.html:2205-2208`); a populated snapshot with an empty `item_order` renders an empty-state line; and `stale: true` renders a visible staleness indication, because `DashboardState.last_updated` is rewritten every 2s by a different loop (`poller.py`) so the page reads fresh while the board's data may be days old. Neither state self-hides — every existing panel renders its section shell and swaps only inner content. Acceptance: the three states produce three mutually different rendered strings, and all three contain the `§ 11` label. **Phase**: Triage board panel

15. **An epic with zero active children renders honestly**: `build_epic_map` seeds its map with every epic id including zero-child ones (`build_epic_map.py:135-175`), so this is reachable the moment a non-terminal epic's last active child completes. No sampled repo exercises it, so it has no live coverage. Acceptance: a fixture with one epic and zero children renders that epic's section with an explicit "no active children" line, not an empty section body and not a suppressed section. **Phase**: Triage board panel

16. **The panel conforms to the dashboard's design system**: `DESIGN.md:94-105`'s Visual Evaluation Criteria weight Information clarity and Consistency High. The panel uses design tokens rather than raw values, and carries the polled-panel doc-line convention — a `.stream-line` whose trailing `ml-auto` span reads `refresh · 30s`, following `backlog_panel.html:28` (the only current 30s instance; `feature_cards.html:20` is the same shape at 5s, and `metrics_baseline.html` spends that slot on a threshold instead and is not the model). Acceptance: over `triage_board.html`, `grep -cE '#[0-9a-fA-F]{3,6}\b'` = 0, `grep -cE '(bg|text)-gray-'` = 0, `grep -cE 'style="[^"]*[0-9]+px'` = 0 per `DESIGN.md:58-68`'s forbidden-patterns table; `grep -c 'refresh · 30s'` ≥ 1 and that string sits inside the template's `stream-line` div. *Information clarity:* `Interactive/session-dependent: status hierarchy and at-a-glance scannability are legible only in a rendered browser view, which DESIGN.md:105 routes to screenshot review rather than a string assertion.* **Phase**: Triage board panel

## Edge Cases

- **`backlog_snapshot is None`** (never polled, or non-local backend, which #411 clears to `None`): loading state, distinct from empty (R14).
- **Populated snapshot, empty `item_order`** (`cortex/backlog/` absent or itemless — measured in `hall-dental`, `Team-Builder-Bot`): empty-state line, section shell retained.
- **`stale: true`**: visible indication; the frozen `polled_ts` is the honest timestamp, not `last_updated` (R14).
- **Epic with zero active children**: explicit line (R15).
- **Item in both `ready` and `deferred_tag`**: shown in ready with the tag flag — correct per the feed, and the deliberate divergence from `/cortex-core:dev`.
- **Item in `ineligible` with `kind: "status"`**: rendered with its `reason` (R4) — this is the live case for #156 and #295.
- **Unknown status / type / priority**: raw passthrough (R10).
- **`blocked_why` entry with `title: null`**: renders `#<ref> (<status>)`, never a blank — live today for `412`'s blocker.
- **Epic key that is non-numeric or absent from `items`**: that epic's section renders under its raw key with no title; the rest of the board is unaffected. The board must not copy `triage.py:263-265`'s bare `except Exception`, which silently degrades the whole map to `{}`.
- **CDN unreachable**: `base.html:11-13` loads htmx, idiomorph, and Tailwind from public CDNs with no local fallback, so `hx-swap="morph"` names an unregistered extension and `<details>` state falls back to the `sessionStorage` restore alone. Pre-existing; the board still renders.

## Technical Constraints

- Only `test_routes_smoke.py` blocks CI (`.github/workflows/validate.yml`), it asserts solely HTTP 200 per route, and its fixture drives `TestClient` **without entering the lifespan**, so no poller runs and the new route is exercised by CI on the never-polled branch alone. The template and fixture tests this ticket adds run only under `just test`'s `tests-dashboard` (`justfile:546-547`), which no GitHub workflow invokes. Stated so the coverage claim is honest.
- `observability.md`'s "dashboard total refresh ≤ 7s" is diverged from by the 30s cadence this panel needs; `backlog_panel.html` already diverges. An unrecorded requirements conflict, named here as input to #415 rather than inherited silently.
- `observability.md`'s Dashboard Inputs list names only overnight session state; the backlog corpus appears in no Inputs list, and #411 already recorded "No requirements-doc basis exists".
- `DESIGN.md:70-81`'s palette table is stale — none of its six hex values appears in `base.html`, which now carries a parchment-default `@theme` block with `html[data-stain="carbon"]` overrides. `base.html` is the authoritative token source; `DESIGN.md`'s forbidden-patterns table and Visual Evaluation Criteria remain current.
- `cortex_command/dashboard/` is not lifecycle-gated (`CLAUDE.md:28`), and `.githooks/pre-commit`'s path matchers exclude it. Only the shared commit-message hook applies.
- `templates/` must never gain an `__init__.py` (`app.py:60-70`).
- `grep -c` counts matching lines, so any acceptance criterion phrased as a grep over rendered output is sensitive to markup line breaks; the criteria above assert over parsed rendered content or over template source files, never over "the rendered strip" as if it were a file.
